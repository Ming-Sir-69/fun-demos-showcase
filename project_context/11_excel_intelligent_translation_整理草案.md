# Excel Intelligent Translation 整理草案

> 状态：待铭哥确认
> 说明：以下内容是对外版本的第一版整理提案，不代表已经最终定稿。

## 1. 对外版本建议保留什么

建议优先保留：

1. 项目总入口与一句话问题定义
2. `project_context/` 中能证明架构演进、分类审计、GUI 准备和复盘思想的高密度文档
3. `src/` 中的核心代码结构
4. `app.py`、`run.sh`、`build_mac.sh`、打包说明等能证明可用性的入口材料
5. 测试样本、示例输入和可执行产物中最能证明稳定性的部分
6. 字典、双路策略、格式保护、并发与重试这几条核心机制说明

## 2. 对外版本建议删什么

建议优先删除或隔离：

1. `.venv/`、`venv/`、`__pycache__/`、`build/` 等环境和缓存噪音
2. 重复的打包产物与重复的 App 副本
3. 与主线无关的历史归档脚本
4. 不适合直接外发的原始业务测试文件
5. 直接点名 `SIP`、`PMP` 的表述，如果它们会造成行业敏感联想

当前高噪音区：

1. 双虚拟环境目录
2. `dist/` 下重复打包结果
3. 临时测试 Excel 与锁文件
4. `archive/` 中与主线无关的历史脚本

## 3. 快读路径怎么设计

建议快读路径控制在 3 层：

### 第 1 层：这是什么

回答：

1. 这是一个工业级 Excel 零损耗智能翻译工具
2. 核心不是“翻译”，而是“复杂格式不坏、长期越用越好”

### 第 2 层：为什么值得看

回答：

1. 它解决了真实而难的格式保护问题
2. 它体现了本地与线上双路、知识复利和成本控制
3. 它已经被验证为可直接使用

### 第 3 层：证据在哪里

快速跳转到：

1. 项目概览
2. 架构白皮书
3. 分类审计
4. GUI 与打包入口

## 4. AI 深读路径怎么设计

建议 AI 深读顺序：

1. `project_context/01_project_overview.md`
2. `project_context/05_Architecture_Evolution_Whitepaper.md`
3. `project_context/04_Classification_Audit_Report.md`
4. `project_context/项目复盘与架构思想总结.md`
5. `README.md`
6. `src/core/` 与 `src/gui/`
7. 入口脚本与打包说明
8. 长文本上下文与必要的测试材料

## 5. Phase 2 验收标准建议

对外信息架构设计阶段，通过标准建议为：

1. 首屏入口能在 1 分钟内说清项目痛点与价值
2. 人类读者能在 3 分钟内定位“稳定、可用、成本友好”的证据
3. 人类读者能在 5 分钟内理解双路策略、格式保护与知识复利
4. AI 能从深读路径中恢复出架构演进与关键取舍
5. 去掉环境噪音与重复产物后，项目主线更清晰而不是更空

## 6. 当前最需要铭哥决策的点

1. 对外是否保留打包产物，还是只保留打包说明和截图级证据
2. 含 `SIP`、`PMP` 字样的描述是改写泛化，还是彻底移除
3. 原始测试 Excel 样本保留到什么程度，才既能证明真实性，又不引发边界风险

## 7. 当前已知证据缺口

这个项目的原始 Session 证据链弱于 `solution-diagram-workflow-mvp`。

原因：

1. 当时使用的是 `TRAE solo`
2. 当时的开发环境没有像现在这样把 Session 无损落到本地
3. 当前 `project_context/` 中保留的更多是 AI 转录后的摘要、白皮书和复盘，而不是逐轮原始对话

这意味着：

1. 它不适合承担“完整原始思考链条展示”的职责
2. 但它仍然适合承担“可运行 Demo + 架构取舍 + 产品化落地”的职责

## 8. 当前补偿策略

既然原始 Session 缺失，就不强行把它包装成“原始上下文完整”的项目。

对外应强调的证据改为：

1. 可运行 Demo
2. 架构演进文档
3. 分类审计与白皮书
4. GUI 与打包思路
5. 样本文件与入口脚本

换句话说：

这个项目的优势不再是“完整保留未经加工的思考痕迹”，而是“虽然缺少原始逐轮对话，但仍然保留了足够强的落地与取舍证据”。
