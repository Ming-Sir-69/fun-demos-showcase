# 项目定义

## 1. 项目目标

本项目不是单纯“挑两个项目给面试官看”，而是把以下三件事同时做成一个完整交付：

1. 选出 2 个适合对外展示的小项目。
2. 把这 2 个项目整理成低认知负担、可快速阅读、可继续深挖的对外版本。
3. 把“筛选与整理方法”本身也整理成一个可展示的大项目。

当前默认范围冻结为“1 个大项目 + 2 个小项目”。

说明：

1. 候选池可以暂时保留 3 个强候选。
2. 当前已完成收缩，正式整理对象确定为 2 个。
3. 后续不再回到“三项目并行展示”路线，除非出现新的强约束。

## 2. 大项目的角色

大项目本身承担以下职责：

1. 说明为什么选这两个项目，而不是其他项目。
2. 说明整理时采用了什么信息结构、阅读路径和验收标准。
3. 说明在有限资源下，如何控制改动范围、迭代次数和换路节点。
4. 为后续读者提供总入口，避免其直接陷入零散文件。
5. 控制最终交付的阅读体量，避免“信息更全但更难读”的反效果。

## 3. 小项目的交付目标

每个小项目的对外版本都要满足：

1. 有完整可读的项目主线。
2. 有足够证明“已真实开发落地”的证据。
3. 有可展示的 Demo 或等价交付物。
4. 有可供人快速浏览的短路径。
5. 有可供 AI 深入分析的长文本材料。

## 4. 筛选标准

筛选时优先看以下维度：

1. 非涉密，不触碰 8D、SIP、PMP 等已明确排除项。
2. 开发完整度高，不是只有构思或空壳。
3. 有 `project_context` 或其他足够支撑真实开发过程的上下文材料。
4. 不过于基础，能体现系统思维、产品思维、验收思维或流程设计能力。
5. 整理成本可控，适合在有限资源下做出高质量对外版本。
6. 与大项目和另一个小项目组合后，不产生明显的结构重复。

## 5. 正式小项目

当前正式小项目为：

1. `solution-diagram-workflow-mvp`
2. `Excel intelligent translation`

当前非正式但可参考项目为：

1. `AI产品经理作品集`

## 6. 验收时新增的要求

以下内容不作为筛选前置条件，但属于整理后的必交付项：

1. 阅读引导文件，例如 `README`、`INDEX` 或等价入口文件。
2. 面向人类读者的快速阅读路径。
3. 面向 AI 的深度分析路径。
4. 对阅读边界、顺序和重点的清晰说明。

## 7. 阅读引导的边界

阅读引导文件必须遵守：

1. 不写对铭哥的主观评价。
2. 不写对铭哥的客观标签化描述。
3. 不做情绪化表达。
4. 不替读者下结论。
5. 只定义如何读取、比对、分析项目材料。

## 8. 记录策略

为了降低重复加工成本，记录分两层：

1. 短文本层：`project_context/` 中只保留关键决策、规则、待定项和验收标准。
2. 长文本层：完整对话与推理过程统一保留在 `project_context/transcripts/`，供 AI 深读，不单独再写一份“历程总结”。

## 9. 组合层面的取舍原则

项目是否入选最终两项，不只看单项强弱，还看组合后的整体效果：

1. 两个小项目最好分别承担不同功能。
2. 至少一个项目负责证明深度工程与系统落地能力。
3. 至少一个项目负责证明信息架构、人机交互或展示设计能力。
4. 若某个项目与大项目本身承担的功能过于重合，则优先降级为备选。
