# 可复用错误索引

来源：`flowchart-layout-engine` 旧项目错误沉淀，以及本工作区通用经验。

## 错误模式 E1：把工具边界问题误当成参数问题

- 症状：为了追求像素级结果，持续调布局、路由、间距，结果始终卡在局部最优。
- 预防：新项目复刻前先做可映射性预检，只验证 draw.io 擅长的企业方案图，不把它当美术工具。

## 错误模式 E2：单指标改善掩盖整体退化

- 症状：某一项看起来更好，但阅读顺序、交叉、文字或容器关系变差。
- 预防：只接受联合验收；任何结论都必须同时检查结构、文字、路由、色彩和交付可用性。

## 错误模式 E3：验收口径不一致

- 症状：编辑器里看到的效果与最终导出、复核结果不一致。
- 预防：所有 AI 验收统一基于最终产物 `.drawio/.svg/.pdf`，不基于口头描述。

## 错误模式 E4：文字与几何脱节

- 症状：文本后补式处理导致框图过密、标签超框、路由空间被挤占。
- 预防：固定字号层级，优先短标签、自动换行与自动尺寸，不追加复杂几何约束。

## 错误模式 E5：导出链路与交付场景脱节

- 症状：编辑器内效果正常，但导出到 SVG/PDF/PPT 后样式损坏或可编辑性不足。
- 预防：每张图都验证 `.drawio`、`.svg`、`.pdf`，若需入 PPT 再补一轮验证。

## 错误模式 E6：本地 SVG 预览与嵌套模块渲染不一致

- 症状：使用 `modules` 容器时，standalone SVG 预览中子节点位置错位或堆叠到左侧。
- 已验证：这不是手动 `position` 导致的。即使改为工具自动布局，只要仍是多模块嵌套，预览依旧会塌缩。
- 预防：本轮 AI 验收统一改用“显式容器节点 + 绝对 bounds”，避免把预览链路误当成布局错误。

## 错误模式 E7：把“轻度失真”误判为“结构成功”

- 症状：单模块纵向图仍能阅读，但容器和节点已经发生偏移，容易被误认为链路稳定。
- 预防：验收时不只看“能不能读”，还要检查容器是否真正包住所属节点；轻度错位同样判为不通过。

## 错误模式 E8：把 standalone SVG 的直线预览误判为连接器失败

- 症状：`.drawio` XML 已经写入 `orthogonalEdgeStyle`、`jumpStyle` 甚至 waypoint，但导出的 standalone SVG 仍显示为斜线或简化折线。
- 预防：连接器验收优先看 `.drawio` 中的 edge style / waypoints，以及官方编辑器或 Desktop 导出结果；不要仅凭 preview SVG 否定路由方案。

## 错误模式 E9：waypoint 和显式 connection point 混用

- 症状：为了给分叉边分面，给同一条边同时写 `waypoints` 和 `exitX/exitY/entryX/entryY`，造成 validator 持续报警。
- 预防：复杂边优先二选一：
  - 要么纯 `waypoints`
  - 要么纯官方编辑器自动分面
  不把两套控制策略叠加到同一条边上。

## 错误模式 E10：把技能运行环境缺口误判为路线失败

- 症状：`drawio` 技能源码存在，但本地缺少 `node_modules/js-yaml`，CLI 直接报 `ERR_MODULE_NOT_FOUND`，容易被误判为 draw.io 路线不可用。
- 预防：每次进入新路线前，先做一次最小命令预检；若是技能依赖缺口，先修执行环境，再继续正式预算轮次，不把环境故障记入路线输赢。

## 错误模式 E11：把装饰线条当成连接器源节点

- 症状：为了复刻顶部输入汇聚线，把一条细横线直接建成节点并作为多条边的共同出发点，导致 validator 报告短终段、共享走廊冲突，预览也出现放射状斜线。
- 预防：装饰横线只负责视觉表达；真正承载出边的应是独立锚点节点，不能把同一根装饰线既当装饰又当连接器源。

## 错误模式 E12：在深色卡片里直接塞整段多行 label

- 症状：把标题和说明整体写入卡片 label 后，文字容易在预览中被挤压或与连接线重叠，难以精确控制视觉节奏。
- 预防：对深色主卡片优先使用：
  - 空卡片背景节点
  - 独立标题文本节点
  - 独立说明文本节点
  这样比单个多行 label 更稳定。

## 错误模式 E13：把 HTML 排版直接写进 YAML label

- 症状：为了实现 `<br>`、`span`、行内样式，把 HTML 片段直接写进 label，转换时报 `Math text must not contain HTML tags`。
- 预防：YAML label 默认保持纯文本；需要复杂排版时，优先拆成独立文本节点，不在主 spec 中塞 HTML 标签。

## 错误模式 E14：自定义 image 节点使用 `none` 颜色

- 症状：虽然图能生成，但 validator 会持续报 `Invalid color "none"`，制造无关噪音，影响真实质量判断。
- 预防：即使是 `shape: image` 节点，也给 `fillColor/strokeColor` 填合法十六进制颜色，通常直接复用其所在背景色。

## 错误模式 E15：把缺少 Desktop 导出能力的环境当成“可完整交付环境”

- 症状：`.drawio` 和 standalone `.svg` 能生成，就误以为整条 Route A 已可交付；但真正需要的 PDF/PNG 官方导出链条并不闭环。
- 预防：凡是把 draw.io 当最终交付工具的路线，必须先确认：
  - 是否有 draw.io Desktop
  - 是否能稳定拿到官方 viewer 或官方导出静态件
  否则只能算“结构路线可用”，不能算“最终交付路线可用”。

## 错误模式 E16：把熄屏或锁屏状态下的系统截图当成图形验收证据

- 症状：截到的是系统壁纸、锁屏画面或睡眠态，而不是浏览器中的真实图，导致对工具结果作出错误判断。
- 预防：凡涉及 viewer 验收，优先使用：
  - 实时 app state
  - 用户明确提供的浏览器截图
  - 当前前台窗口截图
  不使用来源不明的系统级全屏截图作为正式判据。

## 错误模式 E17：把“证据链不完整”误写成“路线失败”

- 症状：图本身未必失败，但由于 viewer 未打开、屏幕权限缺失、静态件没截到，就把整条路线直接判死。
- 预防：失败原因必须分类写清：
  - 结构失败
  - 工具失败
  - 导出失败
  - 证据链失败
  若只是证据链失败，在用户允许时应追加单轮复核，而不是直接固化为终局失败。

## 错误模式 E18：把系统级授权弹窗期间的半完成画布误判为正式验证结果

- 症状：工具本身已进入编辑器，甚至已经导出过静态图，但中途出现 macOS 权限弹窗或 App 数据访问授权；如果此时继续硬做，最终只会得到“半成品 + 被遮挡证据”。
- 预防：
  - 一旦出现系统级授权弹窗，立即把当前状态标记为 `阻塞（待人工授权）`
  - 不把它记成路线失败
  - 只记录已经真实拿到的证据：编辑器可进入、导出是否可用、正式验证是否完成

## 错误模式 E19：把上下文存档脚本路径漂移误判为“项目未记录”

- 症状：技能文档引用了 `~/.Codex/scripts/transcript_manager.py`，但当前机器该脚本路径不存在；如果直接照抄执行，会误以为上下文无法沉淀。
- 预防：
  - 先区分“脚本缺失”与“项目无记录”是两回事
  - 在脚本恢复前，至少把续跑所需状态写回：
    - `12_continuation_handoff.md`
    - `10_route_validation_log.md`
    - `outputs/reviews/`
  - 后续再单独修复 transcript 工具链

## 错误模式 E20：在飞书白板里直接手写 raw OpenAPI JSON

- 症状：为了追求“一步到位”，直接手写 `whiteboard +update --input_format raw` 的整份节点 JSON；复杂图常出现字段校验失败，或者虽然能写入，但后续样式和结构不可维护。
- 预防：
  - 飞书官方白板路线优先使用 `DSL -> whiteboard-cli -> OpenAPI -> +update`
  - `raw` 只作为 whiteboard-cli 的中间产物和最终写入载体
  - 如确需改 `raw`，只允许做小范围、可追踪的确定性补丁，不回到“整份 JSON 手写”

## 错误模式 E21：把飞书 CLI 的 `@file` 语法当成任意绝对路径输入

- 症状：`whiteboard +update --source @/absolute/path/file.json` 直接报参数校验失败，看起来像接口错误，实际只是 CLI 路径规则不匹配。
- 预防：
  - `--source @file` 只使用当前工作目录内的相对路径
  - 若产物路径较深，先切到目标目录再执行
  - 或改用 `--source -` 从 stdin 管道传递，避免路径歧义

## 错误模式 E22：把“控制更细”误当成“结果更好”

- 症状：为了保证结构一致性，给 draw.io 增加过多的显式约束，例如固定过多 bounds、强制拆字块、强制指定连接走廊；结果虽然更可控，但反而压制了工具原生的自动吸附、自动分流和自动避让能力。
- 预防：
  - 后续研究 draw.io 时，把“少约束版本”和“重约束版本”作为一组对照实验
  - 不默认把“更多 spec 字段”当成“更专业”
  - 先判断工具原生能力是否已经足够，再决定是否加约束

## 错误模式 E23：把飞书白板 DSL 能跑通误判为“已经掌握官方流程图方法”

- 症状：CLI 授权、DSL 写入、OpenAPI 更新都成功了，就容易误以为已经掌握了飞书的官方绘图方法；但实际视觉结果仍存在线型差异弱、主链出线重叠、分类框语义不一致等问题。
- 预防：
  - 把“接口可调用”和“方法已掌握”明确分开
  - Route B 后续优化优先研究：
    - 白板 DSL 的流程图场景范式
    - 连接器线型控制
    - 分类框与内容框的语义分层
    - 更少手工补丁、更多原生流程图表达

# Route A 问题点整合（2026-06-16）

## 终止原因总结

Route A / draw.io 在 Round 3 复核后冻结，最终人工视觉验收失败，原因如下：

1. **最终人工验收 4 个失败点**：图例不可读、平台关系歧义、AI 层与业务层缺少显式流动、业务层双向箭头不清晰

4. **证据链问题**：standalone SVG 预览与官方 viewer 表现不一致，导致多次误判

## 错误 E27：把"骨架可读"误判为"视觉验收通过"

- **我们想做什么**：在 Route A Round 1 中验证 T1-A + T1-C 骨架
- **错误内容**：Round 1 初次 AI 验收判定"通过"，但随后撤回，改为"不通过"
- **为什么错误**：把"结构骨架可读"误判成了"视觉验收通过"；实际画面完成度与目标图差距过大，顶部岗位层完全缺失，业务系统层和平台底座层只有空容器
- **尝试过程**：
  1. Round 1 初次验收 → 判定"通过"
  2. 复核后发现视觉完成度不足 → 撤回判定，改为"不通过"
  3. 重新定义验收门槛：只要大面积空骨架、主视觉区块缺失、整体画面明显像半成品，就必须直接判定"不通过"
- **最终方案**：重新定义验收标准，不再把"骨架通过"等同于"视觉通过"
- **预防**：
  - 验收时必须同时检查结构完整性和视觉完成度
  - 不能只看"能不能读"，还要看"像不像目标图的骨架气质"
  - 只要画面明显像半成品，直接判不通过，不写"骨架通过"

## 错误 E28：把 standalone SVG 的直线预览误判为连接器失败

- **我们想做什么**：在 Route A Round 2 中验收正交连接器的真实性
- **错误内容**：standalone SVG 预览把复杂正交连接器显示为直线或斜线，导致误判连接器失败
- **为什么错误**：standalone SVG 渲染器对正交连接器的支持不完整，不能作为最终否决依据
- **尝试过程**：
  1. Round 2 用 standalone SVG 验收 → 发现大量斜线
  2. 怀疑连接器方案失败
  3. Round 3 用官方 viewer 复核 → 连接器正常显示
  4. 确认 standalone SVG 不能作为最终否决依据
- **最终方案**：连接器验收统一以官方 viewer 或官方编辑器为准
- **预防**：
  - standalone SVG 只做补充预览，不作为最终否决依据
  - 连接器真实性必须以 `.drawio` XML 和官方 viewer 渲染为准
  - 当 standalone SVG 与官方 viewer 表现不一致时，以官方 viewer 为准

## 错误 E32：draw.io SVG base64 内联不渲染 — 三种方案均失败（2026-06-17）

- **我们想做什么**：在 draw.io 文件中用 `shape=image` + `image=data:image/svg+xml;base64,...` 嵌入 SVG 线条图标，替代 emoji
- **错误内容**：所有 24 个 SVG 图标在 draw.io viewer 中均显示为占位符（空白带边框），无法渲染
- **为什么错误**：
  1. draw.io 官方文档明确说明："SVGs and raster images aren't native shapes" — `shape=image` 对 SVG 的渲染支持不完整
  2. GitHub issue #1167/1407 记录了类似问题（base64 图片格式错误导致占位符）
  3. 即使代码格式正确，draw.io 对 base64 SVG 通过 `shape=image` 嵌入的渲染支持不可靠
- **尝试过程**：
  1. 方案 A：`shape=image;image=data:image/svg+xml;base64,...` → **占位符**
  2. 方案 B：将 SVG 转为 PNG 28×28，用 `shape=image;image=data:image/png;base64,...` → **占位符**（PNG 同样不渲染）
  3. 测试添加 `imageBackground=none;aspect=fixed` → **待铭哥测试**
  4. 测试 HTML `<img>` 标签直接在 value 中嵌入 → **待铭哥测试**
  5. 降级方案：用 Pillow 直接渲染整个图为 PNG → 结构 OK，但**连接器非正交路由**，视觉不专业
- **最终方案**：HTML `<img>` 标签嵌入到 value 属性中（铭哥人工验证通过）。这是唯一可行的方式
- **预防**：
  - draw.io 的 shape 渲染引擎和 HTML label 渲染引擎是两个独立的系统。嵌入图片走 HTML label 渲染
  - 在批量嵌入前，先用 1 个图标做 MVP 验证

## 错误 E33：强制 1:1 画幅导致垂直利用率低（2026-06-17）

- **我们想做什么**：按 Style Guide 7.1 节要求，将画布从 1600×900 改为 2000×2000（1:1）
- **错误内容**：改后图例在最底部，中间大段空白，内容只用了高度的 45%
- **为什么错误**：T1 图自然比例约 1.8:1（横向布局 —— 4 层自上而下 + 每层最多 8 个卡片横向排开），强制 1:1 破坏了内容的自然密度

## 错误 E37：HTML 文本提取正则未处理嵌套标签，导致文字消失（2026-06-17 v6→v7）

- **我们想做什么**：v6 中自动从 backup 的 value 中提取标题和描述，重建为"图标+粗体标题+小字描述"的规范结构
- **错误内容**：`sec`（Security & Compliance）节点的文字完全消失，只剩图标。root cause 是正则 `re.search(r'<b>([^<]*)</b>', value)` 无法处理 `<b>` 内含 `<br>`（如 `<b>Security<br><font>NDA 合规</font></b>`），匹配到 `<br>` 就停了
- **为什么错误**：`[^<]*` 遇到任何 `<`（不仅是 `</b>`）就会停止，而 `<br>` 和 `<font>` 都是 `<` 开头
- **尝试过程**：
  1. 用 `[^<]*` 提取 `<b>` 文本 → 碰到 `<br>` 就停
  2. 没考虑到原始 HTML 中嵌套标签的可能性
- **最终方案**：先提取 `<b>...</b>` 全部内容（允许内含 `<br>` 和 `<font>`），再以 `<br>` 为界分隔标题/描述
- **预防**：
  - 正则提取 HTML 文本时，不要用 `[^<]*` 做贪婪截断，优先用 HTML parser 或更宽容的正则（如 `<b>(.*?)</b>` + `re.DOTALL`）

## 错误 E38：独立文本标签未通过 source/target 连接，导致拖动时标签不跟随（2026-06-17 v6→v7）

- **我们想做什么**：`label_data`（业务数据/系统接口）和 `label_support`（知识/编排/审计支撑）作为连线上的说明文字
- **错误内容**：这两个标签是独立的 `vertex` 节点，靠绝对坐标放在线上。没有任何连线的 `source` 或 `target` 引用它们。用户拖动其他节点时连线跟着动，但标签不动——它和线没有结构上的连接关系
- **为什么错误**：v5/v6 脚本只改了标签的 value 和 geometry，没有修改它和周围连线的关系。draw.io 中只有 `source`/`target` 引用才能建立结构关系，纯坐标定位是"浮萍"
- **尝试过程**：
  1. v5：把标签文字写到边上（edge label）→ 失败，显示为空
  2. v6：改回独立节点但调整了位置 → 位置对了，但仍无连接关系
  3. 铭哥指出"拖动连线的端点时标签不跟着走"
- **最终方案**（v7 计划）：标签节点改为连线路由中的中间节点。原 `group_existing → master`（1条线）改为 `group_existing → label_data → master`（2条线，经过标签节点）。连线段不带箭头（`endArrow=none`），防止标签"接收"不存在的输入
- **预防**：
  - 任何需要"依附于"某条线的元素，必须通过 source/target 引用建立结构连接
  - 自检规则：解析 XML，验证每个标签节点的 id 是否被至少一条 edge 引用

## 错误 E39：连线图层顺序错误导致虚线被框图覆盖 + 与实线/双向箭头重叠（2026-06-17 v6→v7）

- **我们想做什么**：`e_infra_master` 知识流虚线从 `group_infra`（新建基础设施）连到 `master`（主控 Agent）
- **错误内容**：
  1. 知识流虚线在 XML 中声明最早 → 渲染在最下层 → 被随后声明的 `group_existing`（现有系统框）覆盖
  2. 知识流虚线与 `e_group_exchange`（左右双向箭头）在双组之间路径交叉
  3. 接近 master 节点时，知识流虚线与 `e_existing_master`（主要数据实线）从相近方向进入，视觉重叠
- **为什么错误**：draw.io 的渲染顺序 = XML 声明顺序。先声明的在下层。跨层连线如果比中间层的分组框更早声明，就会被覆盖。此外多线共享同一 source 节点时未指定不同的 exit 坐标，导致在 master 附近碰撞
- **尝试过程**：
  1. v5：将知识流 4 条线移到 `group_existing` 之前声明 → 放在分组框之下是为了让它们从框"下方"穿过，但产生了覆盖问题
  2. v6：同上逻辑 → 虚线仍被框覆盖
- **最终方案**（v7 计划）：
  - 知识流虚线移到 `group_existing` **之后**声明（确保渲染在框上层）
  - 用 waypoint 控制路由：从 group_infra 右侧出发 → 绕到 group_existing 上方 → 到达 master
  - master 入口处错开：知识流虚线走上方入口，主数据实线走左方入口
  - 双向箭头保持原路径不动
- **预防**：
  - 跨层连线必须检查中间层分组框的位置，确保连线路径不穿过：
    1. 任何分组框的包围盒
    2. 其他连线的路径段（共享像素范围 < 5px 时判定为重叠）
  - 多线共享同一目标节点时，必须在不同 `entryX`/`entryY` 错开
  - 自检规则：每产出 drawio 后自动检查所有 edge 的包围盒是否与 vertex 的包围盒重叠
