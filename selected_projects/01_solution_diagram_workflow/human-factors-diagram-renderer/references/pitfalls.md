## 1. 图标嵌入：shape=image 不渲染

**症状**：独立 `shape=image` 的 mxCell 在 draw.io 中显示为空白占位符（带灰色边框）。

**根因**：draw.io 有两套独立的渲染引擎：
1. **Shape 渲染器** — 渲染 mxCell style 中的形状（rectangle、diamond、image 等）。对 base64 图片支持不稳定。
2. **HTML label 渲染器** — 渲染 mxCell value 中的 HTML，由浏览器原生引擎驱动。

`shape=image` 走 Shape 渲染器，而 `<img>` 标签走 HTML label 渲染器。两者不互通。

**正确做法**：用 HTML `<img>` 标签嵌入 value 属性：

```xml
<mxCell value="&lt;img src=&quot;data:image/png;base64,...&quot; width=&quot;22&quot; height=&quot;22&quot;/&gt;&lt;b&gt;标题&lt;/b&gt;" .../>
```

**不要尝试**：
- ❌ `shape=image;image=data:image/...` — 无论 SVG 还是 PNG 都不渲染
- ❌ `imageBackground=none` 或 `aspect=fixed` — 无帮助
- ❌ 独立 image cell 链接方式 — 同样不渲染

## 2. N 计数错误（最常踩的坑）

**症状**：层间距偏小（100px 以下），连线密集时没有呼吸感。

**根因**：只看标签框的数量（M）来代表 N，忽略了没有标签的裸线也穿过间隙。

**案例**：T1 架构图第2-3层间隙。初步以为 N=2（两个标签框），实际 N=5（还有3条从基础设施组到编排层的裸虚线）。N=2 时 G=100px → 不够；N=5 时 G=139px → 正确。

**正确做法**：
1. 遍历 XML 中所有 edge
2. 检查每条边的 source 和 target 是否在间隙两侧
3. 合并不分裂的对（A→标签→B 算 1 条逻辑线）
4. N = 穿过间隙的逻辑线总数，M = 其中有标签的数量

## 3. 返回连线从目标节点侧面穿入

**症状**：返回线从主控Agent的左侧或右侧水平穿入节点 body，而非从顶部或底部正交进入。

**根因**：所有返回路径的最后一个 waypoint 的 x 坐标不在目标节点的 x 范围内。连线只能正交转弯，但最后的入线方向是水平的。

**正确做法**：检查每个连线最后方式点的 x 坐标是否在目标节点 [x, x+w] 范围内，y 坐标是否对齐节点顶部或底部边缘。

```
目标节点：x=300, w=250 → x 范围 [300, 550]
最后方式点：x=265 → ❌ 不在范围内
修正：x=370（在 [300, 550] 内），y=215（约节点底部）
```

## 4. Rail 与层背景底部不对齐

**症状**：层轨（Layer Rail，左侧深色竖条）比层背景短，底部悬空。

**根因**：Rail 和背景是两个独立的 mxCell，坐标独立计算。常见的错误是 Rail 的 y 从 125 开始、背景从 110 开始，或 Rail 的 h 比背景的 h 小。

**正确做法**：检查每层的 Rail 底部 y + h 是否等于背景底部 y + h。

```python
assert bg_y + bg_h == rail_y + rail_h, "Rail 与背景底部不对齐"
```

## 5. 标签在层背景范围外

**症状**：分发标签（如"下发 JSON 任务包"）超出了所属层的背景范围，浮在两层之间。

**根因**：标签 y 坐标是在间隙内计算的，但没有检查它是否超出了所属层背景的底部边界。

**正确做法**：标签节点要么完全在层内部（y + h < 层背景底部），要么成为独立胶囊嵌入连线路径中（拆分 edge）。

## 6. 卡片颜色用错（新 Session 高频）

**症状**：编排层的节点用了深蓝色（#3F6EA8）以外的颜色，或专家层用了编排层的蓝色。

**根因**：新 Session 没有读取色彩字典，而是从目标参考样本（如 Azure 架构图）中推断颜色。

**正确做法**：直接查 `02_风格参考.md §功能色彩字典`，每个 hex 值硬编码。不要从任何样本文件反向推断。

## 7. 跨层连线被层背景遮盖 + 箭头被节点覆盖（‼️ 最关键）

**症状**：跨层虚线穿越层背景时中间段消失；或箭头被节点填充色覆盖不可见，拖到空白处又可见。

**根因**：draw.io 中后声明的元素渲染在上层。箭头不见是因为**所有边声明在目标节点之前**——节点在后，渲染在上，把箭头埋住了。

之前我们错误地理解为"跨层边必须在层容器之前"，实际这是不对的——边在层背景之下就会被层背景遮住，但如果**所有边都在节点之后**，边就在节点上面渲染，箭头不会被覆盖。

**正确做法**：XML 声明顺序规则如下：

```
正确的 XML 声明顺序：
1. 画布背景（bg）
2. 所有层背景（bg_l3, bg_l2, bg_l1）      ← 这些在最底层
3. 所有层轨（rail_l3, rail_l2, rail_l1）
4. 所有节点/卡片（含标签、图例文字）       ← 节点在中间层
5. 所有边（所有 edge=1 的 mxCell）          ← ✅ 边在所有节点后，确保箭头不被遮挡
```

注意：边放在层背景之后但节点之前时，边会出现在节点上方，同时**不会穿越层背景**（层背景在最底下，边在覆盖层上）。

**自检方法**：
1. 找到 XML 中最后一个 `vertex="1"` 的 mxCell（最后一个节点）
2. 找到第一个 `edge="1"` 的 mxCell（第一条边）

## 8. 版本命名混乱

**症状**：baseline V10、renderer v10、chart2 v10 混在一起，文件一多后很难判断“这是渲染器版本”还是“图表轮次”。

**根因**：多个维度共用同一套 `v10` 命名，版本语义没有拆开。

**正确做法**：使用三段式命名。

```text
renderer package build note, for example b010
chart01_layered_architecture_r01.drawio
chart02_decision_tree_r02.drawio
```

命名规则：

- `renderer_bXXX` 或包内版本说明表示 renderer build
- `chartXX` 表示第几张图
- `rXX` 表示该图自己的验收轮次
- 不再单独使用模糊的 `v10` 命名来代表不同维度

## 9. 判断树条件使用原生 edge label

**症状**：条件文字贴在线上，拖动文字时线不跟随，位置密集、不可控、易互相遮挡。

**根因**：draw.io 的 edge label 更适合短标签，不适合承载判断树里的完整条件说明。

**正确做法**：把条件转成显式节点，而不是边标签。

```text
Q1 → 条件 A → R1
Q1 → 条件 B → R2
Q1 → 条件 C → R3
Q1 → 条件 D → R4
```

条件节点推荐使用 `flow_condition`，保持胶囊或轻量节点风格。

## 10. 同端口策略不区分图型

**症状**：架构图里同视觉家族合流没有问题，但判断树里多个分支共用一个端口后，分支不清晰、回读困难。

**根因**：把 `layered_architecture` 的端口复用策略原样套到了 `flowchart_decision_tree`。

**正确做法**：

- `layered_architecture`：同视觉家族可共用端口，优先整体整洁
- `flowchart_decision_tree`：多个条件分支必须 fan-out，优先分支辨识度

先按 `diagram_type` 决定端口策略，再做线型复用，不要全图一种端口规则到底。
3. 检查第一个 edge 是否在最后一个 vertex **之后**
4. 如果是 → ✅ 正确；如果不是 → ❌ 箭头可能被覆盖

```python
def check_edge_order(xml_text):
    root = ET.fromstring(xml_text)
    cells = root.findall(".//*[@id]"    )
    last_vertex_idx = max((i for i, c in enumerate(cells) if c.get("vertex") == "1"), default=-1)
    first_edge_idx = min((i for i, c in enumerate(cells) if c.get("edge") == "1"), default=-1)
    if first_edge_idx > last_vertex_idx:
        print("✅ 所有边在所有节点之后，箭头可见")
    else:
        print(f"❌ 边(#{first_edge_idx}) 在节点(#{last_vertex_idx}) 之前，箭头可能被覆盖")
```

## 12. 标签进出箭头（⁉️ 高频——chart1 每轮必犯）

**症状**：标签节点（胶囊型的边注释，如"下发 JSON 任务包""返回各自视角结论"）的入线带有箭头，语义上变成了"箭头流向标签"，但标签只是注释不是流程目标。

**决策树**：
```

  ├─ YES → 入标签端 endArrow=none;endFill=0;
  └─ NO  → 正常 block 箭头 endArrow=block;endFill=1;
```

**案例**：chart1 中 5 条入标签边全部错为 block 箭头。label_dispatch、label_return、label_report、label_reject、label_approve 的入线全部应为 none。

## 13. 出口方向选择错误——路径绕远路（⁉️ 高频——chart1 重复犯错）

**症状**：边从源节点顶部出口，但目标在源的左方/右方，导致路径"先向上走再绕回来"，路线长且经过空白区域。

**决策树**（基于源和目标中心点相对位置）：

```
dx = target_center_x - source_center_x
dy = target_center_y - source_center_y

|dx| < 30 且 dy > 0  → 出口=下    入口=上    弯折=0  （直下）
|dx| < 30 且 dy < 0  → 出口=上    入口=下    弯折=0  （直上）
dx > 0 且 dy > 0     → 出口=右→下 或 下→右   弯折=1  （右下）
dx < 0 且 dy > 0     → 出口=左→下 或 下→左   弯折=1  （左下）
dx > 0 且 dy < 0     → 出口=右→上 或 上→右   弯折=1  （右上）
dx < 0 且 dy < 0     → 出口=左→上 或 上→左   弯折=1  （左上）
```

**通用原则**：先沿一个方向走到目标对应坐标，再换方向。避免"走过头再折回来"。

**自检方法**：对每条边，计算 target 中心相对于 source 中心的 (dx,dy)，按上表判断出口方向。如果最终 waypoint 序列不符合最优路线（多了不该有的弯折或走了反方向），标记为失败。

## 14. 多条并行路线重叠（总线缺失）

**症状**：多条边在同一路径上完全重合，视觉上像一条粗线（如 4 条分发线在 x=800 同一垂直线段上重叠 161px）。

**决策树**：
```
有多条路径从同一区域的出口到同一区域的入口？
  ├─ YES → 合并为一条总线（无箭头），从总线分支引出带箭头线路到各 target
  └─ NO  → 保持独立路由
```

**总线实现方式**：
1. 源 → label（总线入口，无箭头）为一条边
2. 独立的垂直/水平线段（sourcePoint→targetPoint）作为总线
3. 从总线到各 target 的水平/垂直分支（带箭头）各自独立

## 17. 节点出口选择导致穿入其他节点身体

**症状**：一条边的垂直段穿过非目标节点的 body 区域（如驳回线 x=570 穿过 exp_sqe body）。

**预防规则**：
1. 列出所有节点的 x 范围 `[left, left+width]`
2. 边选择出口方向时，检查 if 该出口的 x 坐标落在任何非目标节点的 x 范围内
3. 如果会穿过 → 调整出口 x 到最近的安全间隙中
4. 安全间隙 = 相邻节点右/左边缘之间的空隙

```python
# 出口 x 安全检查
def safe_x(candidate_x, all_boxes, target_id):
    """检查候选出口 x 是否穿过任何非目标节点"""
    for nid, (x, y, w, h) in all_boxes.items():
        if nid == target_id: continue
        if x < candidate_x < x + w:
            return False  # 穿过此节点
    return True
```

## 8. 画幅比例卡死导致垂直利用率低

**症状**：内容只占画布的 45%，底部大片空白。

**根因**：强制使用 1:1 画布（如 2000×2000），而多层架构图天然是 1.8:1 以上的横向比例。

**正确做法**：默认 16:9（1600×900），让内容决定实际比例。结构偏向横向时保持自然比例。

## 9. 图标语义重复

**症状**：同一图标被不同职能的节点使用（如 cpu 图标同时用于主控Agent和Dify编排引擎），读者产生混淆。

**根因**：分配图标时只看"够不够用"，没检查"是否用在相同语义的节点上"。

**正确做法**：一个职能类别 = 一个图标。分配后统计每个图标的使用次数和用户列表，检查用户职能是否相同。

```python
icon_usage = Counter(icon_name for icon, field in NODE_ICONS.values())
for icon, count in icon_usage.items():
    if count > 1:
        users = [nid for nid, (ic, _) in NODE_ICONS.items() if ic == icon]
        print(f"⚠️ {icon} 被 {users} 共用 — 检查是否同职能")
```

## 10. 连线标签因"删除+重建"而丢失

**症状**：预期有标签的连线变成了裸线。

**根因**：清空旧标签节点后，同步创建 edge label 的代码路径没有正确执行。删除成功但创建失败。

**正确做法**：任何"先删再建"的操作，必须在脚本末尾验证新元素存在性。edge label 的 value 不应为空。

## 11. dark mode 下颜色反转

**症状**：draw.io 中原本的暖白背景在显示器中变成了深色/黑色。

**根因**：draw.io 在 macOS 暗黑模式下默认启用 Adaptive Colors，会自动反转浅色以提高对比度。

**正确做法**：在 draw.io 中设置为 View → Theme → Light。导出的 PNG/PDF 不受影响。

## 12. 单图 draw.io 页签名丢失

**症状**：把单个 `.drawio` 文件拖进 diagrams.net 后，底部页签显示默认的 `Page-1` / `第 1 页`，而不是图表名称。

**根因**：只看画布标题是不够的。draw.io 的工作簿页签来自 XML 的 `<diagram name="...">`，不是画布上的标题文本。如果最终输出文件没有写入或没有保留这个属性，界面就会显示默认页名。

**预防**：

- 每个单图文件固定写 `pages="1"`
- 每个单图文件固定写 `<diagram name="{page_name}">`
- 生成后必须检查最终落盘文件，而不是只检查 renderer 内存结果
- 多页工作簿不作为正式交付物，避免把“多页页签可见”误认为“单图页签已正确”

## 13. 图例颜色和泳道背景混淆

**症状**：底部颜色图例看起来像是在解释泳道背景色，用户不确定它是在说明节点类型还是责任主体。

**根因**：泳道背景和节点填充使用了接近的颜色；图例又使用普通小色块，缺少“这是节点颜色”的形态提示。

**预防**：

- 泳道背景使用更浅的低权重色，只做分区
- 节点颜色保持更明确的语义权重
- 颜色图例必须标为 `节点颜色`
- 图例色块画成“小型圆角节点缩略框”，不要画成普通色块
- 泳道已有标题时，不额外写泳道颜色图例
